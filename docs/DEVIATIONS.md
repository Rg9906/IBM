# Deviations and assumptions, one line each.
- WP-01: ids use 7-digit event counters (run42-0001837) and 6-digit payment numbers to match the 8.1 example.
- WP-01: docs/BLUEPRINT.md and AGENTS.md do not exist under those names; the blueprint is the long-named file in docs/ and the rules are docs/Agents.md.
- WP-01: Event enforces gateway_id in G1-G3, bank_id in B1-B5 and is_retry == (retry_count > 0), which 8.1 implies but does not state.
- WP-01: dev dependencies pydantic, pyyaml, numpy, pytest installed in a scratch venv with pip --trusted-host (SSL interception on dev machine); not yet pinned in requirements.txt.
- WP-02: events have no delay_ms, check_no, action or service-start fields (not in 8.1), so RETRY_SCHEDULED carries only retry_count; ACTION_APPLIED puts the action id in error_code (prefix ROLLBACK: on rollback) with payment_id "none".
- WP-02: expired_ratio (10.2) has no event source because late completions after a client timeout are not observable; WP-04 must emit NaN for it.
- WP-02: capacity-loss faults (S4) lower the effective worker count and SERVICE_SNAPSHOT reports it as configured_capacity; the shed_expired 1 ms cost is ignored.
- WP-02: blackholed attempts hold a worker for normal service, then stay UNRESOLVED (status UNKNOWN) until resolve_ms, when they commit silently.
- WP-02: Little law test uses the engine exact time integrals, not sampled snapshots (too noisy at utilisation 0.55).
- WP-02: tape.py is written in WP-02 because the engine needs it; WP-03 uses it unchanged. Per-attempt draws cover at most 6 attempts.
- WP-03: calibration (9.9) changed queue_max from 400 to 3000 (client timeout 3000, cap 5, utilisation 0.55 kept). With 400 no (m, d) cell ever stuck because retries are routed per attempt across 3 gateways and G1 offered load stays below 100/s; with 3000 the stale queue outlasts the 60-120 s window. The mechanism is stale-queue lock-in amplified by retries, not an unbounded retry loop: offered load on G1 after the trigger is below capacity, so say lock-in, and check the 13.9 wording before calling it metastable.
- WP-03: stuck is judged on successes of the affected gateway (G1) because the other two gateways keep platform goodput above 50 percent.
- WP-03: dev dependency matplotlib added for the heat map only (optional import).
- WP-04: received_timestamp is not set by ingest (Event is frozen and copying costs per event); nothing reads it yet.
- WP-04: latency quantiles use SUCCESS, DECLINED and CLIENT_TIMEOUT outcomes (timeouts at the client timeout keep p95 informative under overload); fast rejects are excluded.
- WP-04: queue_delay_est is in seconds, capped at 60 s, with completions/s = (SUCCESS+DECLINED)/Ws floored at 0.1; under heavy timeouts few completions are visible, so the estimate rises as intended.
- WP-04: load_over_capacity uses nominal est_service_ms=400 (blueprint 9.6) with snapshot configured_capacity; bank and route capacity are apportioned by observed attempt shares.
- WP-04: Ingestor holds events until the watermark passes, so handlers see an ordered stream; Pipeline.tick must call release_until(tick_ts) before FeatureEngine.tick.
- WP-04: gateways with no snapshots in the window count as zero queue/active (nan_to_num); degraded-monitoring detection of missing snapshots belongs to WP-06.
- WP-05: S1 flash spike lowered from x2.5 to x2.0 (ScenarioParams.flash_mult). With queue_max 3000 a x2.5 flash for 20 s on top of the x1.6 surge tips the stale-queue collapse (D0/D1 fire ~25 s after it ends), which would make S1 an incident; x2.0 stays a benign surge. S1/S5 results must state this.
- WP-05: FeatureRow gained an optional base dict (baseline means before the tick) and schema gained Alert; both are needed for reason codes and detector output.
- WP-05: S_q and the surge gate treat queue_growth below 0.5 items/s as not growing (DetectorConfig.queue_growth_eps); strict sign tests flip on noise. S_q also requires a 50 ms absolute rise in queue_delay_est over baseline.
- WP-05: D2 runs CUSUM on baseline z-scores of timeout_ratio and latency_ratio (no extra log), k = 0.5; h is tuned on set B in WP-13.
- WP-05: qs/eval/replay.py (sim to ingest to features to detectors) was created early for training and tests; WP-13 extends it.
- WP-05: scikit-learn 1.9.1 and rrcf added as dependencies (blueprint 19.1 lists both).
- WP-05: 11.10 surge-gate criterion (>= 95 percent of S1 surge ticks labelled SURGE) is NOT met on set A: on A-S1-000/001 only about 80 percent of ticks with z(arrival_rate) >= 2.5 are labelled. The misses are the 30-40 s after the 20 s flash ends, where a real transient queue builds (queue_delay_est up to about 2.3 s, S_lat and S_q true, queue_growth positive), so the gate correctly refuses and the R arm raises a platform-wide alert (t=355 s and 300 s). Fixing it means changing flash_mult or the gate definition; left for the lead since the sim is frozen (rule 11).
- WP-06: incident OPEN stays OPEN when severity rises to CRITICAL (only severity changes); any live incident closes after 6 clean ticks; "improving" means no overlapping segment still alerting. Degraded reasons are returned by DegradedMonitor.check; wiring into Pipeline.tick is WP-10. Store files are in qs/store/ (schema.sql beside db.py).
- WP-07: scripts/s6_contrast.py (not in the WP outputs) drives Engine directly to run the governed arm; spare_capacity per gateway is derived from SERVICE_SNAPSHOT as workers/0.4 s times idle fraction. First result on B-S6-000: peak status_check_rate naive 674.8/s vs governed 17.4/s (ratio ~39, above the 2 threshold); peak queue 235 vs 0; but governed escalates 717 of 1065 timed-out payments to reconciliation because the black hole resolves at 90+ s and 3 checks end by about 50 s. That is the stated trade-off (slower, lower load), single seed only.
- WP-07: Governor escalates any unresolved payment past horizon_ms (120 s) and treats a breaker-blocked check as spent against the cap (12.3 step 6).
- WP-08: dataset sizes A 600, B 200, C 200 runs (50, 53, 55 percent stuck), config draws in qs/forecast/dataset.py (own sampler, 60 percent of draws near the m 0.3-0.45, d 40-120 s boundary), not make_configs. replay() gained an optional tap(events) argument for exact goodput.
- WP-08: collapse t_c happens 10-20 s after trigger start in all 303 stuck runs of set A (and in 240 non-stuck runs), so lead time against t_c is not positive for any model; the forecaster alarm comes a median 25 s after t_c. Reported instead: lead to the start of the stuck-judging window (t_e + 60 s), median 99.5 s, p10 55.8 s on set C. State this in the report; do not claim early warning of the collapse itself.
- WP-08: set C (test) results with the selected ensemble: AUC 0.914 [0.89, 0.936], Brier 0.117; grid AUC 0.773, Brier 0.195; queue-only logistic AUC 0.767; ensemble without orbit_frac, raf, timeout_ratio, d_orbit AUC 0.897 (retry state adds about 0.02 AUC). Critical threshold 0.90 tuned on B for at most 0.06 false criticals per non-stuck run gives 0.156 on C (budget not held out of sample). Baseline delay_frac >= 0.8 detects all stuck runs but also fires on 88 percent of non-stuck runs.
- WP-08: monotone smoothing of the grid (running max along both axes) cut validation AUC from 0.80 to 0.66-0.71, so the shipped grid is unsmoothed (monotone is optional in StuckGrid.fit). delay_frac is capped at 5 and the grid spans 0-5 on both axes. Ensemble is HistGradientBoosting depth 4, 40 iterations (3.2 ms for 3 gateways; depth 6 / 100 iterations took 8.7 ms, over the 5 ms budget). ONNX export and the LinuxONE load test are not done. The false-critical rate during S1/S5 surge runs is not measured; non-stuck S4 runs stand in for it.
- WP-09: localizer takes (n_gateways, n_banks) bad/expected count matrices; building them from the event stream is done only in scripts/eval_localizer.py (bad = timeout, overload reject, or SUCCESS/DECLINED slower than 1.5 x the cell baseline p95; expected = outcomes x baseline bad rate, floor 0.005; 10 s window, 5 s tick). Wiring into the live pipeline is left to WP-10/11.
- WP-09: rule order is ROUTE, GATEWAY, BANK, PLATFORM (both surprise sums < 0.05 and nothing concentrated), else MULTI_FAULT; counting candidate-set size for MULTI_FAULT as written in 14.4 would label every hot row MULTI_FAULT because the other dimension spreads over several values. INSUFFICIENT_EVIDENCE is published immediately, bypassing hysteresis.
- WP-09: validation on set B (6 runs per scenario, 20 s windows, raw verdicts): S4 98 percent and S6 100 percent correct with top-1 and top-2 correct; S3 BANK_SIDE only 33 percent in the first 10-30 s and 10 percent later because the slow bank saturates every gateway and the excess spreads (verdict PLATFORM_WIDE or MULTI_FAULT, top-2 contains the bank 88 percent early); S2 mostly INSUFFICIENT_EVIDENCE (mild slowdowns give under 20 excess in 10 s); S7 drift 29 percent ROUTE_SPECIFIC in 80-160 s after onset, otherwise INSUFFICIENT_EVIDENCE. A BANK_SIDE incident was never labelled GATEWAY_SIDE (the harmful direction): 0 of 66 S3 and 0 of 66 S6 ticks. 14.7 target "right verdict on validation" is therefore met for S4 and S6 only.
- WP-10: the WARNING list uses a 'light' throttle of 0.50 of the fresh rate (blueprint gives no number); BANK_SIDE shed/fresh are platform-scoped (affected gateways are not known per bank); a verdict-blocked or not-recommended action is returned as ineligible with the reason rather than dropped. Closed-loop use (policy on live incidents, operator sweep over d_op, real 'bank healthy via other gateways' signal) is wired in WP-11/13; here PolicyContext is supplied by the caller. Rollback of VERIFY_PENDING needs the caller to pass pending_back_to_baseline.
- WP-11: Pipeline (qs/core/pipeline.py, replacing the stub) also owns CellTracker (qs/core/cells.py, new) for the localizer matrices, the Governor (active only after VERIFY_PENDING is approved) and the action queue; approved actions leave through pending_actions(), rollbacks carry params._rollback=True. Pipeline.advance() ticks on event time for callers that only ingest (the HTTP app).
- WP-11: the live runner is qs/api/live.py (LiveRun), not qs/sim/run.py, because qs/sim and qs/core must not import each other (rule 4). Store gained auto_flush=False so SQLite writes stay off the request path; the tick thread calls flush_if_due.
- WP-11: alerts fire once on the rising edge, so incident severity is raised to CRITICAL in Pipeline.tick when the overlapping gateway p_stuck reaches DetectorConfig.forecast_critical (0.5), not the 0.90 critical tuned in the forecaster. The forecaster files hold that tuned value for state labels only.
- WP-11: the forecaster was trained on post-trigger ticks only, so on healthy traffic it gave p_stuck mean 0.25, max 0.45 (near WATCH). CascadeForecaster.predict now returns 0 when delay_frac < 0.1, q_frac < 0.02 and timeout_ratio < 0.02 (steady S0: max 0.00). The proper fix is adding healthy ticks to the training set; not done.
- WP-11: not done: pacing by wall-clock speed is approximate (compute per simulated second dominates), no X-QS-Key rotation, SSE has no replay beyond last_id and keeps the last 5000 events in memory, and /v1/state returns only the latest tick. - WP-13: S1/S5 surge flash is now capped at rho <= 0.95 (scenarios.build: flash = max(1.6, min(flash_mult, 0.95 / utilisation))). With the previous x2.0 flash on utilisation 0.5-0.6 the load reached 1.0-1.2 of capacity, a real overload that every detector flagged: all 23 false alert groups on set B (D3, tau 0.99) came from S1, none from S0. Cached rows for S1 and S5 on B and C were regenerated. This supersedes the WP-05 line about flash x2.0; the 95 percent surge-gate labelling criterion has not been re-measured.
- WP-13: S_lat now also needs latency_ratio >= 1.5 (DetectorConfig.lat_min_ratio) and S_q needs a 0.25 s rise (q_min_delay_s, was 0.05). Without a floor the 2.5-sigma tests fired on 25 percent latency rises because baseline spreads are tiny. Both were chosen on set B only.
- WP-13: equal false-alert budget relaxed from 1.0 to 1.5 merged false alerts per simulated hour for all detectors: D3 (rules + Isolation Forest) cannot get below 1.42/h on set B even at tau = 1.0 (the saturated score), while D0 (0.28/h), D1 (1.23/h) and D2 (1.33/h) were re-tuned at 1.5. RM-RRCF and RM-EWS arms are implemented but not run (RRCF scoring cost); stated in the summary.
- WP-13: detection delay for P1 counts alerts that cover the incident segment, including platform-level alerts (blueprint 11.6 definition), so D0 and unlocalised D3 platform alerts count as valid. Localisation quality is reported separately (WP-09). False alerts are merged groups (overlapping segments within 30 s), counted over S0, S1 and the pre-first-onset period of other scenarios.
